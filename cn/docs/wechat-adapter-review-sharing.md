# 微信适配器审查与分享导入评估

日期：2026-11-11。范围：当前工作区新增 `WeChatAdapter`、注册与 OCR 路径，以及与其他 adapter 的比较。基准为本对话上一轮添加微信适配器前的实现；包名迁移文件未跟踪，不能用提交间空 diff 代替审查。

后续修复状态：手动 OCR 回退问题已修复。微信能确认当前输入框和标题但无法可靠解析正文时，返回空消息快照，保留会话供手动 OCR 使用；其他审查发现仍待处理。验证结果见 [OCR 回退修复报告](../_reports/wechat-ocr-fallback_report.md)。下文保留审查当时的问题描述。

本次为代码审查与方案分析，未修改业务代码，未进行手机抓取或分享实测。上一轮单元测试通过只能说明受测规则可执行，不能证明真机分类准确。

## Standards

未发现本轮新增 Hook、自动发送或修改目标应用行为。当前包名来自此前改动，不计为本轮新增问题。以下为实现层面的审查发现。

1. **[P1] 手动 OCR 回退被注册适配器破坏。** 服务 `targetFor()` 在有适配器时要求 `extract()` 非空，手动截图又依赖 `targetFor()`。只要微信标题可见但一条长气泡方向不明，正文解析返回空，手动截图也会提前返回。此前未注册微信时顶栏标题路径可以继续。应分开“确认哪个聊天页”和“正文解析是否完整”。见 [服务 targetFor/ocrCaptureManual](../app/src/main/java/com/dianming/phoneapp/MyAccessibilityService.kt) 的 174、636 行。
2. **[P2] 几何坐标基准不支持偏移窗口。** 解析器把绝对屏幕坐标与 `displayMetrics.widthPixels` 比较，右侧分屏的来信可能满足本人消息条件。应以消息列表或已确认窗口为坐标基准，先转换为局部坐标；无法确定时返回未知。见 [WeChatAdapter](../app/src/main/java/com/dianming/phoneapp/capture/WeChatAdapter.kt) 的 15、97–100 行。
3. **[P2] 无效父节点会剪掉全部后代。** 74–76 行在子节点入栈前 `continue`，容器无边界时，其可读正文和输入框也不会被访问。应继续遍历可取得的子节点，仅过滤当前节点的采集资格。其他适配器通常不会因父容器几何无效而中断整个分支。

Standards 共 3 项，最高优先级为手动 OCR 回退失效。

## Spec

需求为“完善微信获取控件树的适配器，区分对方和我发送的”，并保留文档承诺的手动截图入口。

1. **[P1] 手动 OCR 回退回归。** `targetFor → adapter.extract` 与 `ocrCaptureManual → targetFor` 耦合，方向不明、输入框缺失或无正文时同时阻断自动解析和手动截图，与上一轮“手动入口保留”的说明不符。修复应保留明确的会话身份检查，而不是无条件截图或沿用上个会话身份。
2. **[P1] 分屏时可能把对方归为本人。** 宽度 1200、微信窗口横向范围 `[600,1200]`、左侧来信文本横向范围 `[700,1000]`，现有条件会返回 `me`。这是按代码构造的反例，未声称已在手机复现。WhatsApp 用列表内相对边距判断，值得参考。
3. **[P2] 标题数字后缀不是可靠群聊证据。** `GROUP_COUNT` 会拒绝合法联系人名 `客户(3)`，也不能识别没有人数后缀的群聊。WhatsApp 依赖群成员／群头像节点，微信也应优先寻找经过样本验证的结构证据，标题只作辅助。

Spec 共 3 项，最高优先级为手动 OCR 回退与发送方误判。两轴重复发现属于同一问题，不应当作独立缺陷重复统计。

## 与其他适配器比较

| 适配器 | 聊天页依据 | 区分发送方 | 数据基础／限制 |
|---|---|---|---|
| QQ | 正文与特定输入框 ID | 文本两侧距离头像列的关系 | 有历史实测；仍使用显示器几何，不宜直接照搬到分屏 |
| X | 输入框、消息行形态及排除列表标记 | contentDescription 中的发送者标签 | 不依赖气泡左右；文本格式和语言变化仍需验证 |
| 飞书 | 气泡容器、输入框等 ID | OCR 路径用消息容器内发送／已读标记 | 自绘正文走区域 OCR；现有直接文本分支仍按中心点判边，与全左对齐布局存在冲突风险 |
| WhatsApp | 标题、输入框、滚动列表 ID；排除群聊节点 | 列表内相对左右边距，并校验发送状态图标 | 有多份录制树 fixture；四者中最适合作为微信的结构化解析参考 |
| 微信当前实现 | 单个正文 ID、底部 EditText、猜测顶栏标题 | 正文绝对坐标阈值 | 仅观察过一个正文节点；缺完整节点树和真实发送者标注 |

参考 [其他适配器](../app/src/main/java/com/dianming/phoneapp/capture/ChatAppAdapter.kt)、[WhatsApp 规则](../app/src/main/java/com/dianming/phoneapp/capture/WhatsAppAdapter.kt)。飞书直接文本分支的问题是比较过程中发现的既有风险，不计入本次新增微信改动的缺陷数。

当前任一长气泡不满足左右阈值都会使整屏返回 `null`。这是上一轮有意采取的保守策略，但会明显限制覆盖率，不等于已经能稳定读取双方聊天。后续应表达 `NotChat / Readable / Partial / Unreadable`，保留未知身份，并阻止未知身份被下游的 `else -> 对方` 映射。只删除有歧义的最后一条消息也不安全，会让过时内容变成“最新消息”。

## 分享模式是否可行

**应用侧可以增加，微信端具体载荷仍需在当前 Android 版本验证。** Android 支持 Activity 声明分享 action 和 MIME，再读取 `EXTRA_TEXT`、`EXTRA_STREAM` 等输入。现有 Manifest 只有启动入口，没有分享接收声明。[Android 官方接收分享文档](https://developer.android.com/develop/ui/compose/sharing/receive)

外部项目 WeChatBridge 展示了从微信主动选择聊天后接收归档的流程，但其项目以 macOS 为主，不能据此证明本机 Android 会发送同样的 ZIP、TXT 或字段。[WeChatBridge 项目](https://github.com/freestylefly/WeChatBridge)、[作者使用说明](https://github.com/freestylefly/WeChatBridge/blob/main/USAGE.zh-CN.md)

本轮未取得微信 Android 的实际分享 Intent 或文件样本，因此不承诺分享菜单必定显示本应用，也不硬编码 ZIP 内路径、发送者格式或条数上限。

| 实际收到的内容 | 能提取什么 | 还缺什么 |
|---|---|---|
| 普通文本 | 用户选中的文字 | 可能没有发送者、时间和消息边界，需要校正 |
| 截图／多张图 | 本地 OCR 文字与位置 | 说话人、顺序、重叠仍需判断或人工确认 |
| 结构化聊天文本／文件 | 载荷实际包含的发送者、时间、正文 | 必须验证格式；显示名不等于稳定身份 |
| ZIP 归档 | 验证后解析其中已支持的文本及附件引用 | 不能假定 Android 一定提供；需限制展开大小、条目数和路径 |
| 链接／转发卡片 | 链接或摘要 | 不等同于聊天记录，不能凭空补全文本 |

## 推荐实现

1. 新增独立 `ShareImportActivity`。先声明确实能处理的文本和图片 MIME；收到文件样本后再扩展具体归档 MIME，避免无依据注册 `*/*`。
2. 统一处理首次启动和 `onNewIntent()`，识别 `ACTION_SEND`、`ACTION_SEND_MULTIPLE`、`EXTRA_TEXT`、`EXTRA_STREAM` 与 `ClipData`，避免同一 URI 重复导入。
3. 通过 `ContentResolver` 读取授权 URI；先限额保存私有临时副本再异步解析，不能假定临时权限永久有效。坏文件或部分失败保留成功项。
4. 进入导入预览，展示消息、原始发送者、时间及未知字段。让用户指定“哪位是我”和本轮回复对象；“对方”来自用户确认的映射，不依赖屏幕坐标。
5. 保留导入来源和独立会话 ID。复用回复／判断客户端，但先从 Service 抽出可被页面调用的分析用例，避免为了分析导入内容强制开启无障碍。
6. 用户确认后分析；首版只编辑、复制，不因当前前台恰好是微信就自动绑定或回填。仅导入选中批次，不宣称获取完整历史或实时监听。

## 验证顺序

先修复手动 OCR 身份解析耦合并补集成测试；再用完整的公开节点树样本验证本人／对方、长消息、键盘展开、窗口偏移和群聊结构。几何阈值调整必须有发送者标注，不能只改到现有测试通过。

分享入口用两步验证：先以系统标准分享测试接收 Activity，再在本机微信中用测试聊天选择“转发到其他应用”（若该版本提供）。核对本应用是否出现、action、MIME、字段键、URI 权限和可读性。诊断默认只显示字段类型和计数，正文由预览页显示。分别测试文本、图片和多条记录，不把一条成功推断为全部支持。

实现优先级建议：修复已确认回归 → 分享文本／图片预览闭环 → 以实际样本决定归档解析 → 再提升微信节点解析覆盖率。分享模式可作为主动导入入口，节点适配继续服务当前屏幕的实时辅助，两者最终进入同一个经过确认的对话模型。
